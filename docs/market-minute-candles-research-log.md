# GrowAnt 1분봉 누적 연구 일지

- 최초 작성일: 2026-08-11
- 마지막 갱신일: 2026-08-12
- 현재 단계: 과거 기준선 B0 복원, 분봉 구조 리팩터링 검증 완료, B1 증거 보존 구조 부분 완료
- 범위: 국내 주식 5종목, KRX 정규장 1분봉, 차트 조회 전용

이 문서는 1분봉을 수집하고 화면에 그리기까지 수행한 연구를 한곳에 계속 누적하는 기준 문서다. 현재 결론만 적는 보고서가 아니라, 무엇을 왜 시험했고 얼마나 좋아졌으며 어떤 대가가 생겼는지를 실패 기록까지 포함해 보존한다.

## 0. 이 문서를 갱신하는 규칙

문서 위쪽의 현황판과 다음 실험은 최신 상태로 갱신한다. 완료된 실험, 실패, 결정 기록은 삭제하거나 결과를 덮어쓰지 않는다.

- 실험 결과가 바뀌면 새 실험 ID를 만든다.
- 기존 기록이 잘못됐으면 원문을 남기고 정정 ID를 추가한다.
- 성능이 좋아진 결과뿐 아니라 느려진 결과와 실패도 남긴다.
- 관찰한 사실과 그 사실에 대한 해석을 분리한다.
- 원본 JSON, 이미지, 실행 보고서는 별도 파일로 보관하고 이 문서에서 연결한다.
- API 키, JWT, 계정 정보, 허가받지 않은 원천 시세는 문서와 저장소에 넣지 않는다.
- 개인 브랜치에서 연구를 누적하고 조직 저장소 PR에는 최종 채택한 변경과 재현 가능한 검증만 포함한다.

상태 표기:

| 상태 | 의미 |
| --- | --- |
| 계획 | 질문과 실험 방법만 정함 |
| 준비 | 코드·데이터·측정 도구를 준비 중 |
| 측정 | 반복 실행 중 |
| 검증 | 정확성과 결과 재현성을 확인 중 |
| 기준선 | 후보 비교를 위한 최초 측정이며 아직 최적화 결론은 아님 |
| 잠정 | 현재 방향으로 사용하지만 최종 선택은 아님 |
| 채택 | 현재 조건에서 사용하기로 결정 |
| 보류 | 지금은 이득이나 근거가 부족함 |
| 폐기 | 정확성, 권리 또는 비용 조건을 만족하지 못함 |
| 재실험 | 조건이 달라지거나 반복성이 부족해 다시 측정해야 함 |

## 1. 연구 목표와 경계

### 1.1 최종적으로 답할 질문

1. 실제 체결 데이터를 어디서 어떤 방식으로 받아야 하는가?
2. WebSocket, REST, 두 방식의 혼합 중 어떤 구성이 가장 안정적인가?
3. 늦게 도착하거나 중복된 체결로도 정확한 1분봉을 만들 수 있는가?
4. 서버 또는 공급자 연결이 끊겼을 때 누락 구간을 복구할 수 있는가?
5. 분봉 한 개가 PostgreSQL에서 실제로 차지하는 크기는 얼마인가?
6. 종목 수와 보관 기간이 증가하면 저장량, WAL, 백업량은 얼마나 늘어나는가?
7. 인덱스, batch, 파티션, 캐시는 어느 규모부터 가치가 생기는가?
8. 사용자 수가 증가할 때 DB, 직렬화, 네트워크, 클라이언트 중 어디가 먼저 느려지는가?
9. 압축 또는 응답 구조 변경이 실제 사용자 대기 시간을 얼마나 줄이는가?
10. 클라이언트가 많은 분봉과 실시간 갱신을 끊김 없이 표현할 수 있는가?
11. 추가한 기술의 성능 이득이 복잡도와 장애 위험보다 큰가?

### 1.2 이 연구에서 하지 않는 것

- 매수·매도, 주문, 포지션 계산은 다루지 않는다.
- 사용 권한이 확인되지 않은 실제 시세를 공개 화면, 블로그 원본 데이터 또는 조직 PR에 넣지 않는다.
- 병목을 측정하기 전에 Kafka, TimescaleDB, read replica 같은 구조를 미리 도입하지 않는다.
- 짧은 로컬 부하 결과를 실제 가입자 수나 운영 SLA로 환산하지 않는다.
- 평균값 하나로 후보를 선택하지 않는다.

### 1.3 성능보다 먼저 통과해야 하는 게이트

| 게이트 | 통과 조건 | 실패 시 |
| --- | --- | --- |
| G0 권리 | 수집·저장·화면 표시·보관·재배포 범위를 서면 확인 | 공개 사용 중단 |
| G1 정확성 | 예상 행 수와 모든 OHLCV·시간·revision 일치 | 후보 즉시 폐기 |
| G2 복구 | 확정 봉의 미복구 누락 0건 | 운영 후보 제외 |
| G3 격리 | 종목·사용자 데이터 혼입 0건 | 후보 즉시 폐기 |
| G4 안정성 | queue, connection, memory가 계속 증가하지 않음 | 원인 해결 전 확장 금지 |
| G5 성능 | 정한 p95·p99·오류율을 반복 실행에서 만족 | 단순 구조 유지 또는 재실험 |
| G6 시장 의미·계보 | venue·session·interval·원천 source·보정 이력을 추적 | 서로 다른 의미의 봉을 합치지 않음 |
| G7 collector 단일성 | leader와 승계 중 중복·누락 0건 | 다중 인스턴스 수집 금지 |

## 2. 체결 한 건이 차트가 되기까지

한 문장으로 설명하면 실제 거래 기록을 받아 같은 1분 상자에 모으고, 시가·고가·저가·종가·거래량으로 요약해 저장한 뒤 API로 전달하여 시간 위치에 맞춰 그리는 과정이다.

~~~mermaid
flowchart LR
    P["시세 공급자<br/>현재: 비결정적 로컬 sim"] --> C["체결 수집"]
    C --> A["이벤트 시각 기준<br/>1분 OHLCV 집계"]
    A --> W["분 종료 후<br/>5초 대기"]
    W --> Q["저장 대기<br/>pending"]
    Q --> D[("PostgreSQL<br/>확정 분봉")]
    D --> R["JWT REST API<br/>최대 7일"]
    R --> G["gzip JSON"]
    G --> U["Flutter 차트<br/>최신 48개"]
    B["공급자 REST"] -.->|"후속 구현"| V["백필·대조·revision 판단"]
    V -.-> D
    A -.->|"후속 구현"| F["현재 봉 fan-out"]
~~~

현재 구현에는 비결정적 로컬 sim을 이용한 수집→집계→저장 구간과, 결정적 DB 시드를 이용한 저장→REST→Flutter 구간이 각각 있다. B0 화면은 시드를 DB에 직접 넣었으므로 같은 데이터가 수집부터 화면까지 통과한 종단 증거는 아직 없다. 실제 공급자 변환 코드, REST 백필, 수집 담당 서버 하나를 정하는 방식, 현재 봉을 여러 사용자에게 나누는 기능은 구현 전이다.

| 단계 | 현재 상태 | 아직 확인하지 못한 것 |
| --- | --- | --- |
| 공급자 | 현재 시각과 난수를 쓰는 sim으로 수집 동작 검증 | KIS·키움·LS 실제 지연과 권리 |
| 집계 | 역순·중복·1분 경계 단위 테스트 | 실제 장중 대량 체결과 공급자별 sequence |
| 확정 | 분 종료 후 5초, DB 실패 시 pending 유지 | 프로세스 종료 시 진행 봉 복구 |
| 저장 | PostgreSQL 복합키와 revision upsert | 장기 낭비 공간, 백업, 읽기 복제 DB |
| API | JWT, 최대 7일, 시간순 OHLCV | 장시간·분리 장비 부하 |
| 전송 | 1KB 이상 gzip | 압축 level과 Brotli 비교 |
| 차트 | API가 반환한 합성 OHLCV 최신 48개, 누락 구간 공백 | 저사양 기기와 장시간 갱신 |

## 3. 공통 실험 규칙

### 3.1 식별자

| 대상 | 형식 | 예시 |
| --- | --- | --- |
| 실험 | EXP-연도-W주차-번호 | EXP-2026-W33-004 |
| 환경 | ENV-이름-번호 | ENV-LOCAL-M5-001 |
| 데이터 | DS-종류-범위-번호 | DS-SYNTH-5D-5S-001 |
| 증거 | ART-실험ID-번호 | ART-EXP-2026-W33-004-01 |
| 결정 | DEC-연도-W주차-번호 | DEC-2026-W33-003 |
| 정정 | COR-연도-W주차-번호 | COR-2026-W33-001 |

### 3.2 현재 기준 환경

환경 ID: ENV-LOCAL-M5-001

| 항목 | 값 |
| --- | --- |
| 장비 | Apple M5 Pro, 논리 프로세서 15개 |
| 메모리 | 48GiB |
| 운영체제 | macOS 26.5.2, arm64 |
| Java | OpenJDK 21.0.6 |
| Gradle | 9.5.1 |
| PostgreSQL | Testcontainers PostgreSQL 16.14, postgres:16-alpine 이동 태그 |
| Docker | 29.6.0 |
| Docker Compose | 5.1.4 |
| 기준 commit | 58088568e555f2c9a1534bd60720fd1d1a1add24 |

환경이 하나라도 달라지면 동일 실험의 연장으로 보지 않고 새 환경 ID를 기록한다. 최종 운영 판단은 서버와 부하 발생기를 분리한 환경에서 다시 측정한다.

위 표의 macOS와 Docker 버전은 문서 작성 시점에 다시 확인한 현재 환경이다. 과거 B0 실행 당시 k6와 macOS 버전은 기록되지 않았다. postgres:16-alpine은 digest가 고정되지 않은 이동 태그이므로 미래에 같은 명령을 실행해도 PostgreSQL patch가 달라질 수 있다. 다음 기준선부터는 이미지 digest와 k6 버전도 MANIFEST에 포함한다.

### 3.3 데이터셋

| 데이터 ID | 구성 | 용도 | 상태 |
| --- | --- | --- | --- |
| DS-SYNTH-5D-5S-001 | 5종목 × 390분 × 5일 = 9,750봉 | API, 차트 정확성 | 존재 |
| DS-STORAGE-5D-5S-001 | benchmark 전용 5 ticker × 390분 × 5일 = 9,750봉 | relation, WAL, batch | 코드 생성 |
| DS-REPLAY-1D-5S-001 | 5종목 × 390분 × 분당 1,000체결 = 1,950,000체결 | 집계 처리량 | 코드 생성 |
| DS-API-1D-1S-001 | 삼성전자 390봉 | 짧은 조회 부하 | B0 기록 |
| DS-API-5D-1S-001 | 삼성전자 1,950봉 | 긴 조회 부하 | B0 기록 |
| DS-FUTURE-1Y-5S-001 | 5종목 × 252거래일 | 장기 저장·인덱스 후보 | 계획 |
| DS-FUTURE-1Y-100S-001 | 100종목 × 252거래일 | 파티션·동시 마감 후보 | 계획 |
| DS-FUTURE-1Y-1000S-001 | 1,000종목 × 252거래일 | 구조 확장 임계점 후보 | 계획 |

결정적 데이터는 seed, 예상 행 수, 첫·마지막 시각, 전체 필드 대조 결과를 함께 남긴다. 단순 필드 합 checksum은 충돌할 수 있으므로 최종 정확성 검사는 행 전체를 순서대로 비교한다.

### 3.4 모든 후보의 정확성 검사

- 예상 ticker 집합과 종목별 행 수 일치
- 시작 포함·종료 제외 범위 일치
- 허용된 거래 세션 안에서 시간 오름차순을 확인하고 모든 gap을 거래 없음·거래정지·수집 누락으로 분류
- 결정적 교육용 시드는 별도 규칙으로 장중 모든 인접 봉의 1분 간격을 확인
- open과 close의 이벤트 순서 일치
- high와 low 범위, volume, tradeCount 일치
- 중복·누락·잘못된 순서 0건
- 낮거나 같은 revision이 최신 값을 덮지 않음
- 같은 입력을 다시 실행해도 최종 결과가 같음
- API와 DB의 전체 행·전체 필드 일치
- 캐시와 replica에서도 ticker 또는 사용자 데이터 혼입 0건
- 장애 복구 후 원본과 checksum 및 전체 필드 일치

정확성 검사에서 한 건이라도 실패하면 속도 결과는 의사결정에 사용하지 않는다.

### 3.5 측정 반복과 공정성

1. 질문과 가설을 먼저 적는다.
2. 한 실험에서는 핵심 변수 하나만 바꾼다.
3. 동일 commit, 환경, 데이터, 요청 분포를 유지한다.
4. JVM, DB buffer, cache의 cold와 warm 결과를 분리한다.
5. 탐색은 최소 3회, 최종 채택 후보는 최소 5회 독립 실행한다.
6. 기준 A와 후보 B를 A-B-A-B 순서로 번갈아 실행한다.
7. 중앙값뿐 아니라 p50, p95, p99, 최대, 최소, 실행 간 편차를 기록한다.
8. 후보를 측정하는 날 기준선도 다시 실행한다.
9. 최종 용량 판단은 부하 발생기를 별도 장비로 분리한다.
10. 원본 결과와 실행 명령을 남긴다.

신뢰도:

| 단계 | 조건 |
| --- | --- |
| 탐색 | 1회 실행, 방향만 확인 |
| 잠정 | 3회 반복과 정확성 통과 |
| 채택 후보 | 5회 이상 반복, 기준선과 교차 실행 |
| 재현 | 다른 장비 또는 CI에서 같은 방향 확인 |

### 3.6 개선율 계산

지연, 크기, CPU처럼 낮을수록 좋은 값:

~~~text
개선율 = (기준값 - 후보값) / 기준값 × 100
~~~

처리량처럼 높을수록 좋은 값:

~~~text
개선율 = (후보값 - 기준값) / 기준값 × 100
~~~

모든 결과에 다음 두 비교를 함께 적는다.

- 직전 채택 기준선 대비 증분 개선
- 최초 B0 대비 누적 개선

예:

~~~text
p95: 154ms → 110ms
절대 감소: 44ms
개선율: 28.6%
대가: CPU 12% 증가
판단: 사용자 지연 감소가 CPU 증가보다 가치 있는지 단계 부하로 재확인
~~~

### 3.7 임시 합격선과 안전 중단

아래 값은 운영 SLA가 아니라 현재 연구를 비교하기 위한 임시 기준이다.

| 항목 | 임시 기준 |
| --- | ---: |
| HTTP 오류율 | 1% 미만 |
| 응답 검사 성공률 | 99% 초과 |
| API p95 | 200ms 미만 |
| API p99 목표 | 300ms 미만 |
| 확정 봉 저장·조회 가능 시점 p99 | 2초 미만 |
| 공급자 수신 지연 p95 | 1초 미만 |
| 공급자 수신 지연 p99 | 2초 미만 |
| WebSocket 재연결 | 10초 이내 |
| 누락 구간 백필 | 60초 이내 |
| 미복구 확정 봉 | 0건 |

복잡도를 추가하는 변경은 보통 p95 15% 이상, 처리량 20% 이상, 저장량 또는 전송량 20% 이상의 개선이 있을 때 채택을 검토한다. 개선이 작으면 단순한 구조를 유지한다.

다음 조건에서는 시험을 즉시 중단한다.

- 데이터 불일치, 유실 또는 중복 발견
- 오류율 5% 초과가 30초 이상 지속
- p99 2초 초과가 1분 이상 지속
- 메모리 90%, 디스크 80%, CPU 95% 이상이 계속됨
- DB connection 대기 또는 수집 backlog가 계속 증가
- replica lag 또는 retry queue가 회복되지 않음

### 3.8 증거 보관 규칙

각 실험은 가능한 범위에서 다음을 남긴다.

- MANIFEST: commit, 환경, 데이터, 실행 순서
- QUALITY: 행 수, 전체 필드 비교, 누락·중복 검사
- METRICS: p50·p95·p99·처리량·CPU·메모리
- TRACE: 느린 요청 또는 처리 단계의 시간
- FAULT: 주입한 장애와 회복 시간
- DATABASE: query plan, relation, WAL, pool
- SCREEN: 로컬 시험 데이터임을 표시한 화면
- RIGHTS: 사용·저장·표시 권한 확인 결과

원천 시세는 권리 범위가 확인되기 전 저장소에 넣지 않는다. 필요한 경우 집계 통계, 해시, 허가된 짧은 예시만 남긴다.

### EXP-2026-W33-001: 결정적 교육용 시드와 증거 검사

- 질문: 끊어져 보이지 않으면서도 오류를 자동 탐지할 수 있는 5종목·5일 데이터를 만들 수 있는가?

- 기준: 각 분의 시가를 독립 생성한 초기 삼성전자 하루 시드.
- 후보: 종목별 가격 단위, 분당 최대 2틱, 장중 연속, 거래일 경계만 ±2틱인 결정적 시드.

  - 한 ticker 전체, 첫·마지막·중간 봉 삭제와 high + 1 훼손을 모두 탐지.

- 관찰: 교육용 데이터의 장중 연속성은 크게 좋아졌다.
- 한계: 실제 시장은 항상 이전 close와 다음 open이 같지 않다.

## 13. 초보자용 용어집

### 13.1 시장 데이터와 집계

| 용어 | 쉬운 설명 | 이 프로젝트에서의 의미 |
| --- | --- | --- |
| 체결 | 실제로 끝난 거래 한 건 | 가격·수량·시각·순번을 가진 입력 |
| 호가 | 사고팔고 싶다고 제시한 가격 | 아직 끝난 거래인 체결과 다름 |
| 체결 tick | 서버가 받는 체결 이벤트 한 건 | TradeTick 입력 |
| 가격 1틱 | 가격이 움직이는 최소 단위 | 종목과 가격 구간에 따라 다름 |
| ticker | 종목 코드 | 삼성전자는 005930 |
| 1분봉 | 한 분 동안 체결을 요약한 기록 | OHLCV와 체결 수 한 행 |
| OHLCV | 시가·고가·저가·종가·거래량 | 여러 체결을 차트용으로 요약 |
| open | 그 분의 가장 이른 체결 가격 | 서버 도착 순서가 아니라 event time 기준 |
| high | 그 분의 가장 높은 체결 가격 | 정상 체결가의 최댓값 |
| low | 그 분의 가장 낮은 체결 가격 | 정상 체결가의 최솟값 |
| close | 그 분의 가장 늦은 체결 가격 | event time과 sequence 기준 |
| volume | 그 분에 거래된 주식 수량의 합 | 중복 체결은 한 번만 합산 |
| tradeCount | 중복을 제외한 체결 건수 | 한 체결에서 여러 주가 거래될 수 있어 volume과 다름 |
| bucket | 같은 시간 데이터를 담는 상자 | 09:00 이상 09:01 미만 |
| bucketStart | 시간 상자의 시작 시각 | 09시 00분 봉은 09:00:00 |
| event time | 거래가 실제로 발생한 시각 | open과 close의 기준 |
| arrival time | 우리 서버에 도착한 시각 | 네트워크로 실제 순서와 다를 수 있음 |
| sequence | 같은 시각 체결의 순번 | 동일 시각의 open·close 순서 |
| watermark | 이벤트 시각 진행을 보고 늦은 데이터를 언제까지 기다릴지 정하는 기준 | 표준 방식의 후보이며 현재 POC는 정식 watermark를 계산하지 않음 |
| 확정 cutoff | 늦은 체결을 기다리는 POC 마감 기준 | 서버 현재 시각 - 5초를 1초마다 검사해 대략 분 종료 5~6초 뒤 마감 |
| final | 일반 체결 수집을 마감한 봉이라는 표시 | 높은 revision의 보정은 이후에도 가능 |
| 빈 분 | 체결이 하나도 없는 분 | 수집 장애로 잃은 분과 구분 필요 |

tick은 체결 한 건과 가격 최소 단위 두 뜻이 있으므로 체결 tick과 가격 1틱으로 구분해 쓴다.

### 13.2 저장과 복구

| 용어 | 쉬운 설명 | 이 프로젝트에서의 의미 |
| --- | --- | --- |
| pending | 저장 성공을 기다리는 목록 | DB 실패 시 다음 주기에 재시도 |
| backfill | 놓친 과거를 다시 채우는 일 | REST로 WebSocket 단절 구간 복구 |
| reconcile | 우리 값과 공급자 값을 대조해 수정 | 자동 대조는 미구현이며 향후 결과를 높은 revision으로 저장할 경로만 준비됨 |
| upsert | 없으면 저장, 있으면 조건부 갱신 | 높은 revision만 UPDATE |
| revision | 같은 분봉의 버전 번호 | 더 큰 값이 최신 보정 |
| 멱등성 | 반복해도 최종 결과가 같은 성질 | 같은 입력 재실행 결과 유지 |
| 복합 기본키 | 여러 열을 묶은 고유 식별자 | ticker + bucket_start |
| WAL | DB의 장애 복구용 변경 기록 | 관계 크기와 별도로 측정 |
| index | 행을 빨리 찾기 위한 정렬 구조 | 현재 복합 기본키 인덱스 |
| batch | 여러 행을 한 묶음으로 저장 | B0는 9,750행 한 JDBC batch |
| checksum | 결과가 같은지 보는 지문 | 최종 검사는 전체 필드 비교가 더 강함 |

### 13.3 API와 성능

| 용어 | 쉬운 설명 | 읽는 방법 |
| --- | --- | --- |
| REST | 요청할 때 한 번 응답받는 방식 | 저장된 과거 분봉 조회 |
| WebSocket | 연결을 유지하며 계속 받는 방식 | 실시간 체결과 현재 봉 후보 |
| JWT | 인증된 사용자임을 증명하는 토큰 | 분봉 API 호출에 필요 |
| gzip | 원본으로 되돌릴 수 있는 압축 | 동일 JSON의 wire bytes 감소 |
| wire bytes | 실제 네트워크로 전달한 바이트 | JSON 파일 크기와 압축 전후를 구분해 측정 |
| cache | 자주 쓰는 결과의 임시 복사본 | DB를 대체하지 않음 |
| fan-out | 한 데이터를 여러 사용자에게 나눔 | 공급자 구독을 사용자별로 만들지 않음 |
| latency | 한 작업이 끝날 때까지 시간 | 낮을수록 좋음 |
| throughput | 일정 시간에 끝낸 작업 수 | 높을수록 좋음 |
| RPS | 초당 완료 HTTP 요청 수 | 지연과 함께 봐야 함 |
| VU | 반복 요청하는 가상 사용자 | 실제 가입자 수와 다름 |
| p50 | 절반의 요청이 이 안에 완료 | 중앙적인 속도 |
| p95 | 95%의 요청이 이 안에 완료 | 느린 5% 직전 |
| p99 | 99%의 요청이 이 안에 완료 | 드물게 매우 느린 꼬리 |
| soak | 오랜 시간 부하를 유지하는 시험 | 누수와 점진적 저하 확인 |
| SLA | 운영에서 지키기로 약속한 수준 | 현재 로컬 수치는 SLA가 아님 |

자주 생기는 오해:

- 100 VU는 실제 사용자 100명이 아니다.
- p95 통과가 모든 요청의 성공이나 빠른 p99를 의미하지 않는다.
- final은 현재 지연 허용 시간이 지나 일반 체결 수집을 마감했다는 뜻이며 높은 revision 보정은 가능하다.
- 캐시는 원본 DB를 대체하지 않는다.
- 거래가 없던 분과 장애로 잃은 분은 같은 빈칸이 아니다.
- WAL을 영구 테이블 크기에 그대로 더하면 안 된다.
- 체결을 분봉으로 요약하는 것은 원본을 복원할 수 없는 손실 요약이지만 gzip은 무손실 압축이다.
- 현재 WebSocket 백필, Redis cache, fan-out, 실제 공급자 변환 코드는 완료 기능이 아니라 연구·후속 구현 범위다.
